# 第 11 章 两段式混合检索

> **本章目标**：理解 `HybridRetriever` 的漏斗设计——粗召窗口放宽以避免漏召，
> 精排只看"可能有戏"的块，控制昂贵的 LLM 打分次数。
> 分治策略：把"又快又准"拆成 **召回（快、宽）** 与 **精排（准、窄）** 两段，
> 各自优化一个目标。

## 11.1 漏斗设计

`src/retrieval.py:342` 的 `HybridRetriever.retrieve_by_company_name`：

```text
全部 chunk ──向量召回──▶ 28 个粗候选 ──LLM 精排──▶ top 6 ──▶ RAG 上下文
```

- 粗召窗口 `llm_reranking_sample_size=28` **大于**最终 `top_n=6`：
  窗口过小会漏召（精排再好也救不回没进窗口的正确块），过大会成本爆炸。
  代码注释明确：**两段式让精排只看「可能有戏」的块，控制了昂贵的 LLM 打分次数**。
- 融合分排序后取 `top_n` 截断（`reranked_results[:top_n]`）。

## 11.2 参数敏感性

| 参数 | 默认 | 调大的收益/代价 |
|---|---|---|
| `llm_reranking_sample_size` | 28 | 召回更全 / LLM 打分成本线性上涨 |
| `documents_batch_size` | 2 | 单块路径→多块路径，省调用 / 漏块风险升高 |
| `top_n` | 6（各问答配置自行传入） | 上下文更全 / 噪声增多、token 上涨 |
| `llm_weight` | 0.7 | LLM 信号更强 / 失去向量分的稳定补偿 |

注意调用方约定：**`llm_reranking_sample_size >= top_n` 由调用方保证**
（docstring 明说）——没有断言，靠约定。这是"比赛代码"的典型取舍。
