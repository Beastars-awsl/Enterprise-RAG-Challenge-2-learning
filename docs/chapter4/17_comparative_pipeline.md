# 第 17 章 比较题流水线

> **本章目标**：精读比较题的三步法：拆解 → 并行单答 → 汇总。
> 这本质上是 Map-Reduce 思想——分治教科书案例在 LLM 应用中的直接落地。

## 17.1 三步法

`src/questions_processing.py:732` 的 `process_comparative_question`：

1. **拆解**：`get_rephrased_questions`（`api_requests.py:593`）把比较题改写成
   每家公司的独立子题（{公司: 子题} 映射，一次 LLM 调用）。
   改写 prompt 强约束子题与母题**同指标同口径**——口径漂移会让比较失去可比性。
2. **并行单答**：每家一个 future（ThreadPoolExecutor），调
   `get_answer_for_company`，**schema 硬编码 "number"**——比较题衡量的都是
   数值口径，比较语义留给汇总步。各子答的 references 汇聚成全量引用列表。
3. **汇总**：以 schema="comparative" 再走一次问答——此时 rag_context 是
   {公司名: 答案 dict} 的序列化而非页文本；`ComparativeAnswerPrompt` 的
   final_answer 合约是「公司名或 N/A」（含币种不符剔除公司等排除规则，
   语义全在 prompt 侧）。

## 17.2 成本账与容错

- **成本**：每次子答走完整单公司流程（检索 + 生成）；加改写与汇总，
  比较题成本是单公司题的 N+2 倍以上。
- **容错**：**比较题拒绝「缺腿答案」**——任一公司失败（子题缺失 ValueError
  或执行异常）都打印后 re-raise，少一家公司的比较结果是误导性的，
  宁可整题失败、进入 error entry（第 13 章的单题容错在此收紧）。

> **动手**
> 1. 找一道比较题，手动检查改写出的子题是否与母题同指标同口径。
> 2. 从 debug 文件里找一道比较题的记录，数一数它实际发生了多少次 LLM 调用。

> **自测（合并问题）**

> 2. "缺腿答案宁可整题失败"与第 13 章"单题容错"矛盾吗？判定标准是什么？
